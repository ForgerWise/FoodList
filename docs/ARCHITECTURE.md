# Architecture

FoodList is a small, offline-first Flutter app. There is no backend: all user data lives on the device. The only network calls are optional barcode lookups.

## Layout

```
lib/
  main.dart                 App start-up, theme, bottom navigation
  database/
    data.dart               Ingredient model + InputDataBase (the fridge list), openStorage()
    category.dart           Categories: labels, order, icons, legacy-name mapping
    food_catalog.dart       Built-in quick-pick foods, recent items, barcode memory
    languagedb.dart         Chosen UI language
    sub_category.dart(.g)   Legacy type — kept only so old data can be opened (see below)
  page/                     Main screens: home, add/edit, settings
  setting/                  Settings sub-pages
  util/
    theme.dart              Colours and ThemeData (see docs/DESIGN.md)
    app_settings.dart       Theme mode, "expiring soon" range
    barcode.dart            Scanner screen, barcode parsing (GS1), product lookup
    notification.dart       Daily reminder content
    alarm.dart              Daily alarm (runs in a background isolate)
    review.dart             When to ask for a Google Play rating
    onboarding.dart         First-launch welcome dialog
  l10n/intl_*.arb           Source strings (en, zh_TW, ja)
  generated/                Generated by intl_utils — do not edit by hand
third_party/                Vendored plugins patched for Android Gradle Plugin 9
test/                       Unit/widget tests, incl. data migration tests
```

State is kept simple on purpose: pages own their state (`StatefulWidget`) and read/write through the small database classes. There is no state-management package.

## Storage

### Hive box `mybox`

| Key | Shape | Notes |
|---|---|---|
| `INGREDIENTS_LIST` | `List<[categoryKey, name, 'yyyy/MM/dd', quantity]>` | The fridge. Read through `Ingredient.tryFromList`. |
| `CATEGORY_MAP` | `Map<key, label>` | Built-in keys: `meat fish vegetable fruit bean eggMilk mushroom processedfood others`; custom keys: `C<millis>`. |
| `CATEGORY_KEYS` | `List<key>` | Display order. Repaired on load if it drifts from the map. |
| `CATEGORY_ICONS` | `Map<key, emoji>` | Custom icons; built-ins fall back to `kCategoryIcons`. |
| `RECENT_ITEMS` | `List<[categoryKey, name, days]>` | Newest first, max 40. Feeds "Quick pick". |
| `BARCODE_CACHE` | `Map<code, [categoryKey, name, days]>` | Names the user gave to barcodes. In-store codes use `store:<first 7 digits>`. |
| `SUB_CATEGORY_MAP` | legacy | Deleted on load. |

### SharedPreferences

`selectedLanguage`, `theme_mode` (ThemeMode index), `soon_days`, `notificationsEnabled`, `alarmTime`, `category_version`, `onboarding_v1_shown`, `review_first_open`, `review_saves`, `review_last_ask`.

## Data format history — read before changing storage

Users upgrade from any old version, so **every format ever shipped must still load**. `test/migration_test.dart` pins this down; add a case there whenever you touch storage.

| Version | Change | How it is handled |
|---|---|---|
| ≤ 2.x | Ingredient rows were `[categoryDisplayName, subcategory, inputDate, expireDate]`; categories had sub-categories stored as Hive `SubCategory` objects (typeId 1). | Rows are detected by a `String` at index 3 and converted using the translation table in `category.dart` (`legacyCategoryKey`). **`SubCategoryAdapter` must stay registered forever**: Hive decodes every record when a box opens, so removing it crashes users upgrading from those versions. |
| 3.0 | Rows became `[categoryKey, name, expireDate, quantity]`. First launch inserted a "Slide to delete" sample row (2999/09/29). Renaming a category created a new key. | — |
| 3.1 | Sample row replaced by an onboarding dialog. Rename keeps the key. | Sample rows are removed on load. Built-in labels are re-translated only while they still equal a known default translation, so user renames survive language changes. Unparseable rows are kept and written back unchanged. |

Rules of thumb:

1. Prefer keeping the on-disk shape and adapting in code.
2. If the shape must change, detect the old shape, convert it on load, write it back once, and add a migration test.
3. Never drop data you cannot parse.

## Barcode lookup

`parseScan` turns any scanned string into a `ScanInfo`:

- EAN-13/8, UPC-A/E, GTIN-14 → normalised GTIN.
- GS1 element strings (DataMatrix/QR/GS1-128) and GS1 Digital Link URLs → GTIN plus expiry (AI 17 / 15).
- GS1 restricted-circulation prefixes (`02`, `04`, `2x`) → in-store label (weighed fresh food). Never looked up online; remembered by item part.
- Anything else → a personal key the user can name.

`lookupBarcode` tries, in order: the on-device `BARCODE_CACHE`, then Yahoo! JAPAN (first for `45`/`49` prefixes, only if a Client ID was provided at build time), then Open Food Facts. Every source must be free and its terms respected — see the README "Data sources" section.

## Background work

`alarm.dart` schedules one inexact daily alarm (no exact-alarm permission). The callback runs in a separate isolate, so it calls `openStorage()` and loads strings itself before `NotificationService.sendDailyNotification()`.
